RAG RETRIEVAL DEBUGGING SESSION — SUMMARY
==========================================
Scope: backend/RAG/Query/doc_retrieval.py, readar_chat_engine.py — the curated-doc
chat retrieval pipeline (embed -> retrieve_subgraph -> rerank -> build_context).

1. NO VISIBILITY INTO WHERE TIME/QUALITY WAS GOING
   Problem: only one coarse timing bucket (retrieval vs Gemini), no way to see
   which retrieval sub-step was slow or whether results were actually relevant.
   Fix: added per-segment timing (lock wait, DB calls, embed, subgraph retrieve,
   rerank, Gemini TTFB) and per-candidate score logging (cosine/BM25/fused/rerank
   scores, hop distance) throughout the pipeline.

2. COSINE-ONLY RETRIEVAL SILENTLY DROPPED WHOLE TOPICS
   Problem: a single blended embedding for a multi-part question got pulled toward
   whichever sub-topic dominated, burying or entirely missing chunks for the other
   part (e.g. a KeyError/IndexError question also asking about lists/dicts never
   retrieved the KeyError/IndexError content at all).
   Fix: added BM25 (sparse/exact-term) alongside cosine, fused via Reciprocal Rank
   Fusion — BM25 has no such blending, so an exact rare term surfaces regardless.

3. STOPWORD LIST WAS STRIPPING REAL PYTHON KEYWORDS
   Problem: the BM25 tokenizer's stopword list included "with", "except", "as",
   "from", "in", "for", "if" — all genuine Python syntax, so questions about "the
   with statement" or "try/except" got silently broken.
   Fix: trimmed the stopword list to only true filler words (articles, pronouns,
   auxiliary "be"), keeping every word that doubles as a Python keyword.

4. FIXED TOP_K=6 SEEDING DROPPED ENTIRE TOPICS ON MULTI-PART QUESTIONS
   Problem: a 5-concept question (list comprehension / decorators / KeyError+
   IndexError / try-except / imports) only got 6 fixed seed slots total — two full
   topics got zero representation across the whole candidate pool, no matter how
   deep hop-expansion went.
   Fix: replaced fixed top-6 seeding with KEYWORD-DRIVEN seeding — one guaranteed
   seed per extracted keyword/phrase, so seed count scales with actual question
   complexity instead of a fixed number.

5. GLOBAL CONFIDENCE THRESHOLD CRUSHED WEAK-BUT-LEGITIMATE TOPICS
   Problem: a relative score cutoff applied against ONE global top score let a
   strong topic (e.g. "dictionary") silently wipe out a weaker-but-real topic's
   seed and supporting neighbors (e.g. "list", "tuple").
   Fix: made the threshold PER-CLUSTER (each neighbor judged against its own
   seed's score, not the global max) and exempted seeds themselves from the cutoff
   entirely — guarantees every extracted topic keeps at least its anchor chunk.

6. KEYWORD/PHRASE EXTRACTION — THREE APPROACHES TRIED, LESSONS FROM EACH
   a) spaCy POS-tagging (keep NOUN/PROPN only): dropped domain terms that are
      grammatically prepositions/conjunctions in English ("with", "except").
   b) spaCy noun_chunks + dependency rules: fixed multi-word phrases ("with
      statement", "try/except") but excluded verb-anchored phrases entirely
      ("close a file" isn't a noun phrase).
   c) Small local LLM (Qwen2.5-0.5B via llama.cpp, ~400MB, fully offline): gave the
      best semantic phrase grouping, but added ~1-1.5s of generation latency per
      question — rolled back in favor of speed.
   Settled on: blind n-gram windows (1-3 words) filtered by a POS boundary rule
   (span must end on a content word, or be an ADP/SCONJ+NOUN pattern like "with
   statement") — catches both noun and verb phrases without hardcoded lists, at
   near-zero latency (POS tagging only, no generation).

7. BM25-ALONE PHRASE-TO-CHUNK MATCHING HAD NO CONCEPT OF PHRASE ADJACENCY
   Problem: matching an extracted phrase to its best corpus chunk via BM25 let a
   chunk that merely contained the phrase's words scattered in unrelated sentences
   "match" — e.g. "the with statement" matched an unrelated chunk that happened to
   contain both words separately.
   Fix: match phrases to chunks via COSINE similarity against the actual corpus
   embeddings (judges meaning, not word overlap), with BM25 kept only as a
   secondary signal for exact rare-term matches.

8. "@dataclass" WAS SILENTLY DROPPED FROM CANDIDATE GENERATION
   Problem: the word filter rejected any token that wasn't purely alphanumeric,
   so the single spaCy token "@dataclass" (correctly tagged PROPN) was thrown out
   whole because of the "@" — "dataclass" could never become a candidate at all.
   Fix: strip symbol characters per-token instead of rejecting the whole token.

9. MORE SEEDS = MUCH LARGER CANDIDATE POOLS (STRUCTURAL, NOT QUERY-AWARE)
   Finding: hop-expansion (HOP_LIMIT=2, top-3 neighbors by precomputed graph edge
   weight) is entirely static/structural — it has no awareness of the current
   question at all, it just walks "nearest neighbors in the whole corpus," twice.
   More seeds (from more complex questions) means proportionally more independent
   expansion trees, so candidate pools ballooned (12 seeds -> 88 raw candidates on
   the 5-topic question) even though ~50% of that was verified (by manual content
   review) to be irrelevant noise from otherwise-good seeds' hop-neighborhoods.
   Tested HOP_LIMIT=1 vs 2: cut candidate volume ~35-40% with zero loss of the
   exact-match target chunks (they arrive as seeds, unaffected by hop depth) —
   but the NOISE RATIO stayed about the same, confirming noise comes mainly from
   a few weak/generic seed keywords, not from hop depth itself.

10. RERANKER STILL NECESSARY — VERIFIED WITH ACTUAL NUMBERS, NOT ASSUMED
    Checked total retrieved content size per query: simple query fit comfortably
    under the 6000-char context budget, but the complex and vague queries came in
    at 2-3x over budget — meaning some final selection step is unavoidable
    regardless of latency preference. Given noise chunks still make up roughly
    25-50% of what survives retrieval + confidence threshold (worse on vaguer
    queries), and the reranker is the only step that judges genuine query-passage
    relevance (vs. our upstream cosine/BM25 heuristics) before that final cut —
    confirmed it should stay, not be removed.
    *** SUPERSEDED by item 13 below (2026-08-23 session) — candidate volumes
    dropped enough since this was written that the reranker no longer meets its
    own trigger condition most of the time. See item 13. ***

SESSION 2 (2026-08-23) — dedup fix, BM25 removed from phrase matching,
reranker case reversed, ingestion-level chunking gap found
=================================================================================

11. GREEDY OVERLAP-DEDUP COULD EVICT A GOOD STANDALONE CANDIDATE ENTIRELY
    Problem (flagged in session 1, actually fixed this session): in
    keyword_seed_candidates' greedy selection, a higher-scoring multi-word phrase
    claims its full word span and evicts any lower-scoring candidate — including
    standalone words — that overlaps it. A long phrase scores high precisely
    because it captures more of the question's meaning, but that same length
    means it rarely appears verbatim in real corpus text, so its own
    phrase-to-chunk match is often weak or wrong. Confirmed concretely: on "How
    do decorators use closures under the hood?", 'decorators use closures'
    outscored and evicted BOTH standalone 'decorators' and 'closures', then
    itself matched a PEP8 style-guide chunk — losing any chance at real decorator
    content even though it exists elsewhere in the corpus.
    Fix: standalone (single-word) candidates are now exempt from the overlap
    rule and always survive selection independently, regardless of whether a
    higher-scoring multi-word phrase already covers their word position.
    Verified no regression across the full 11-query test set.
    Known residual cost: this makes every multi-word phrase's component words
    ALSO appear as separate seed candidates (e.g. 'decorators use closures' +
    'decorators' + 'closures' all present at once) — visible redundancy, though
    the final candidate list is still always node_id-deduped downstream (see
    item 12), so it doesn't reach the model as literal duplicate content.

12. FINAL CANDIDATE LIST WAS ALREADY DEDUPED BY NODE_ID — VERIFIED, NOT ASSUMED
    Checked directly: even when multiple seed phrases match the identical
    corpus chunk (common after the item 11 fix), retrieve_subgraph's hop-
    expansion BFS already tracks a `visited` set keyed by node_id, so a second
    seed pointing at an already-visited node contributes nothing extra. Ran
    three queries with known same-node seed collisions and confirmed 0
    duplicate node_ids in every final candidate list. The redundancy from item
    11 costs a little extra (harmless) embedding/matching compute upstream, but
    never reaches build_context or the model as duplicate content.

13. BM25 REMOVED FROM PHRASE-TO-CHUNK MATCHING — MEASURED WORSE, NOT ASSUMED
    Problem: item 7 (session 1) added BM25 back as a "secondary signal for
    exact rare-term matches" citing KeyError as the motivating example. This
    session, directly compared cosine-only vs. the hybrid RRF-fused match on a
    battery of real phrases. Finding: for the two cases BM25 was supposedly
    needed for (KeyError, dataclass), cosine ALONE already picked the identical
    correct chunk — BM25 changed nothing there. Everywhere BM25 DID change the
    winning chunk, it was worse: it rewards literal word overlap regardless of
    topic, and this corpus reuses generic words as structural boilerplate across
    unrelated sections (nearly every control-flow section is titled "X
    Statements" — pass/if/for/match Statements — and list-method docs all
    mention "index" generically). Concretely: 'the with statement' vs. BM25's
    pick of an unrelated 'pass Statements' chunk purely because both contain
    the word "statement"; 'IndexError' pulled toward a generic "remove by
    index" chunk instead of the chunk that actually raises IndexError.
    Fix: removed BM25 from keyword_seed_candidates' phrase-to-chunk matching
    entirely — cosine similarity only. This DIRECTLY FIXED the 'with statement'
    query (previously 3/3 candidates wrong, now mostly correct with-statement
    content). Net effect on candidate volume across the 11-query set: mixed,
    not uniformly worse — totals went 166 -> 184 (+11% average), with 3/11
    queries actually smaller and the increase concentrated in 2 outlier
    queries, not systemic. One specific query ("read a file") got measurably
    noisier (lost precise f.read()/readline() chunks, gained generic ones) —
    a real but isolated trade-off, not reversed.
    Also tried: widening phrase-to-chunk matching from single-argmax-winner to
    top-K-per-phrase / relative-threshold, to recover cases where the truly
    relevant chunk ranked respectably (e.g. #66/1049) but not #1. Rejected —
    tripled candidate volume (7->23 unique nodes on one query) while still
    failing to recover the target chunk, since the gap was too large (~84% of
    the winning score) to bridge without flooding in unrelated content at
    similar relative scores. Not implemented.

14. RERANKER CASE REVERSED — CANDIDATE VOLUMES NO LONGER JUSTIFY IT
    Following items 11 and 13, re-checked item 10's justification (reranker
    needed because candidate pools ran 2-3x over context budget). Checked
    rerank_nodes() directly: it early-returns with ZERO effect whenever
    len(candidates) <= RERANK_TOP_N (15) — no reordering, no filtering, pure
    passthrough. Across the current 11-query regression set, most queries now
    land at 3-19 candidates — at or under that threshold most of the time.
    Where it DOES trigger, it can only trim (pool_size - 15) nodes — as little
    as 1 in the cases checked. The reranker was sized for the ~88-candidate
    pools item 9 described before HOP_LIMIT=1 + these fixes; it is not sized
    for what the pipeline produces now. Not yet removed from code, but the
    case for removal is now evidence-backed. See CONTINUE_SESSION.md.

15. TWO TEST QUERIES TURNED OUT TO BE UNFAIR, NOT RETRIEVAL BUGS
    "What's the best way to organize code across multiple files?" and "How do
    decorators use closures under the hood?" both looked like retrieval
    failures (near-zero relevant content returned) and got significant
    debugging effort (top-K matching experiments, rank tracing) before
    recognizing the actual problem: both ask for content this specific
    introductory tutorial never wrote — opinionated best-practices guidance,
    and internals-level mechanism explanation connecting two concepts the
    tutorial doesn't formally cover (closures isn't discussed at all; the
    @dataclass example never uses the word "decorator"). Confirmed via direct
    rank-tracing: the closest available content for "organize code" ranked
    #66/1049 for its best phrase — a real, correctly-identified "closest
    available" answer to a question the corpus can't actually answer, not a
    pipeline defect. Lesson: a RAG system returning weak/scattered results for
    a genuinely out-of-scope question is correct behavior, not a bug to chase.

16. FINAL VALIDATION: 6 FAIR, COMPLEX, MULTI-LAYERED QUESTIONS — 5/6 EXCELLENT
    To confirm items 11+13 actually improved things (not just avoided
    regression), ran 6 fresh questions designed to be genuinely hard — each
    combining 2 real documented topics — but confirmed in-scope this time
    (lesson from item 15 applied). Results: 5/6 excellent, in several cases
    retrieval surfaced the EXACT sentence needed to answer the full compound
    question with minimal surrounding noise (loop-else vs. try-else, singleton
    tuple syntax, scope resolution (LEGB), broad-vs-specific exception
    handling, manual __iter__/__next__ vs. generator/yield). 1/6 partial (see
    item 17) — not a seed-matching or dedup problem, a chunking one.

17. INGESTION-TIME CODE CHUNKING IS THE NEXT REAL BOTTLENECK (NOT YET FIXED)
    Found while diagnosing the one partial result in item 16 (mutable default
    argument question). Read the raw graph nodes in document order for that
    exact tutorial section: the explanation-then-code-then-output sequence is
    split across 6+ separate nodes (e.g. the critical "Important warning: The
    default value is evaluated only once" sentence is its own node, separate
    from both the surrounding explanation AND the code block it explains).
    Checked the graph's edge structure directly: it has exactly C(1049,2) =
    549,676 edges for 1049 nodes — a FULLY CONNECTED graph, meaning "adjacency"
    for hop-expansion is 100% embedding-cosine-similarity-based with ZERO
    concept of document order. Code blocks routinely don't embed close to their
    own prose explanation (different surface form), so hop-expansion can easily
    grab weaker filler sentences from a code example while skipping the actual
    code or its key explanatory sentence — confirmed this happened for real:
    the retrieved context had "will print 5" and "[1]\n[1, 2]\n[1, 2, 3]" but
    NOT the actual code or the warning sentence explaining it.
    Also checked: node metadata already distinguishes `type: 'code'` from
    `'paragraph'`/`'list'` (331/1049 nodes are code), and `dom_ids` appear to
    preserve original document order — the raw material to fix this exists,
    nothing currently uses it.
    Also verified NOT broken: section-heading attachment. All 1049 nodes carry
    a correctly formatted heading prefix; spot-checked one full chapter's
    heading transitions node-by-node against real section numbering — zero
    gaps or mislabeled chunks.
    This is an ingestion/graph-building problem, not a retrieval-logic
    problem — the fix belongs in whatever script builds the .pkl (not found in
    this repo this session, only the pre-built output exists), not in
    doc_retrieval.py. Top priority for next session — see CONTINUE_SESSION.md.
